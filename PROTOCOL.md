# ТЗ и экспериментальный протокол

## Исследовательский вопрос

Как меняется качество распознавания по одному каналу ЭКГ при переходе между сессиями одного человека и к участникам, которых извлекатель признаков не видел при обучении? Сравниваем ручные признаки, сходство временных рядов и представления CNN.

## Пункты 1–7

1. Зафиксировать сценарии, разбиение, метрики и единицу оценки.
2. Дать команде общее Python-окружение и несколько команд для скачивания, подготовки, разбиений и запуска моделей.
3. Собрать доступные записи с исходным ID участника, ID записи и сессией или датой. Сохранять все доступные сессии, включая более поздние, и вести инвентаризацию по источникам.
4. Подготовить одноканальные сигналы целиком. Привести частоту к 250 Гц, применить полосовой фильтр 0,5–40 Гц, центрировать, нормализовать по RMS. Посчитать R-пики для проверки качества и признаков RR. Сохранять исходную длительность, исключения и связь с источником. Не выделять окна или отдельные удары как самостоятельные примеры на этом этапе.
5. Сформировать и проверить манифесты для известных и новых участников. Для всех применяемых методов использовать одни разбиения.
6. Реализовать классическое представление и методы сходства. Признаки уровня записи используют спектр мощности, автокорреляцию, квантили и интервалы RR. StandardScaler и PCA обучаются только на разрешённой обучающей части. Корреляция с ограничением лага и DTW на пониженной частоте доступны для сравнения целых записей.
7. Обучить небольшую 1D-CNN по ID участника и сохранить один нормализованный embedding на запись. Использовать маску при пакетной обработке сигналов разной длины. Проверить обычный backward и сохранение весов.

## Данные и разбиение

Единица примера и оценки — исходная регистрация ЭКГ. Участники имеют ID с префиксом датасета. Совпадающий ID из другого источника не связывается с человеком. Точные копии волны в пределах одного датасета выявляются по хешу исходного сигнала. С исходной даты для ECG-ID и PTB-XL берём календарный день. Две отдельные записи одного дня могут иметь разные ID, но считаются одной группой для строгого теста между днями.

Для Heartprint используем папки `Session-1`, `Session-2`, `Session-3L` и `Session-3R`. Метки S3R и S3L сохраняем в `record_id`; обе подгруппы входят в одну группу S3 при разбиении. В релизе есть точные дубли между S3L и S3R, а также между S1 и S2. Их исключаем до создания разбиений; пары сохранённых и исключённых файлов отражены в `excluded.csv`. При сравнении условий S3 учитываем, что часть исходных файлов содержала одну и ту же волну.

В обоих протоколах для оценки нужно хотя бы две известные группы сессий на участника. Доступные исходники участников с одной известной группой остаются в инвентаризации данных, но в манифесты оценки не попадают. Отдельная запись с неизвестной датой не считается новой сессией.

- `known`: первая сессия каждого участника даёт обучение и эталоны. При наличии двух и более записей в первой сессии одна уходит в `known_val`. Все последующие сессии — `known_query`. Это валидация между отдельными записями той же сессии. При разборе результатов это ограничение нужно явно учитывать.
- `unseen`: приблизительно 60/20/20 по участникам, с фиксированным seed и минимальными размерами групп. Все записи с известной сессией у участников train разрешены при обучении. У других участников первая сессия — enrollment, последующие — query. Группы train, validation и test не делят ни одного человека. Enrollment новых участников формирует эталоны без обновления весов или PCA.

Источник и исходные отведения могут влиять на результаты. Основные сравнения проводим внутри каждого датасета. Проверка переноса между датасетами остаётся отдельным экспериментом.

## Оценка (пункты 8–9)

- Идентификация. Для каждого человека строим эталон из разрешённых записей. Для векторов усредняем нормализованные embeddings и нормализуем эталон. Выбираем человека с максимальным косинусным сходством. Для прямого сравнения записей усредняем сходства запроса со всеми эталонными записями кандидата (для DTW сходство — отрицательное расстояние). Отчёт содержит top-1 accuracy, macro-F1 по участникам, присутствующим в запросах, и число людей и запросов. При равных оценках выбираем первый ID в лексикографическом порядке.
- Верификация. Один запрос сравнивается с заявленным эталоном. Положительные пары имеют одинаковый ID, отрицательные — разные. Для каждого запроса используем одну настоящую пару и до 10 разных чужих ID, равномерно выбранных без возвращения. Выбор фиксирован по seed и одинаков для всех методов на одном и том же разбиении. ROC-AUC и EER описывают качество ранжирования. Отдельно сообщаем FAR и FRR при пороге, выбранном на validation по минимуму `|FAR − FRR|` (при равенстве выбираем более строгий порог). EER интерполируем между точками ROC; это не рабочий порог и он не переносится с теста. Для `known` у источника с недостаточной валидацией перенос порога оговаривается отдельно, без подбора по тесту.
- Новые участники. Выполняем идентификацию и верификацию на `test_query` относительно `test_enroll`. Настройки выбираем через `val_enroll` и `val_query`. Для top-1 считаем 95% интервал бутстрэпом по участникам запроса (1000 повторов при фиксированной галерее); такой интервал не учитывает изменение состава самой галереи. Для сравнения `known` и `unseen` учитываем разный размер галереи и обучающей выборки.

## Стресс-тест (пункт 10)

- Сравниваем PCA, CNN без аугментаций и CNN с аугментациями на тех же разбиениях `unseen` для Heartprint и PTB-XL. У двух CNN совпадают обучающие записи, архитектура, seed, число эпох и размер пакета.
- При обучении с аугментациями с вероятностью 0,5 сохраняем исходную запись, иначе равновероятно добавляем дрейф или полосовой шум. RMS помехи выбирается равномерно в диапазоне 10–50% от RMS записи. Сигнал целиком сохраняет исходный ID и длину. На валидации и в эталонах помеха не добавляется.
- На тесте сравниваем исходный запрос, дрейф 0,25 Гц и полосовой гауссовский шум (фильтр 0,5–40 Гц), каждый при RMS 25% и 50% от RMS сигнала. Помеха добавляется после стандартной фильтрации без повторной нормализации; фаза или реализация шума фиксируется по ID записи и seed, независимо от метода. При смене уровня меняется только масштаб помехи.
- Пороги выбираются на чистой валидации отдельно для каждой модели и сохраняются во всех тестовых условиях. Галерея и пары те же, что в базовом тесте. Такой эксперимент проверяет чувствительность к остаточной помехе на входе модели; реальную смену датчика оцениваем отдельно.

## Идеи следующих экспериментов

Нарезку при необходимости делаем после фиксации манифеста. Каждое окно наследует `record_id`, роль разбиения и границы в отсчётах. Результаты агрегируем до исходной записи. Для SSL две версии фрагмента можно получать только из тренировочных данных выбранного протокола. Небольшие временные смещения можно проверить отдельным экспериментом. Вейвлеты, полноценный SSL и запись с датчика остаются расширениями.
